本文档定义 agent 应如何把 `signal` 和 `question` 推进成真正的洞察。

这里的重点不是“证明自己已经知道答案”，而是：

1. 明确已知事实
2. 提出合理假设
3. 说明还缺什么证据
4. 给出下一步动作

## 一、四层推理对象

### 1. `signal`

客观信号，只回答：

- 看到了什么

### 2. `question`

高价值问题，只回答：

- 为什么这个现象值得关注

### 3. `hypothesis`

原因假设，只回答：

- 可能是什么导致了这个问题

### 4. `action`

后续动作，只回答：

- 下一步应该验证什么、补什么、盯什么

## 二、不要混淆“事实”和“假设”

好的洞察报告必须明确区分：

- 已证实事实
- 推测性解释
- 待验证事项

错误写法：

- “销售集中说明华东战略失败”

更稳妥的写法：

- “销售集中提示存在区域依赖风险。一个可能原因是资源投放过度集中在华东，但还需要区域投放与转化数据验证。”

## 三、常见原因假设方向

当看到一个问题时，优先从这几类原因思考：

### 1. 流程原因

- 录入链路断点
- 责任分工不清
- 审核机制缺失

### 2. 口径原因

- 统计标准不一致
- 汇总逻辑不统一
- 数据版本错配

### 3. 结构原因

- 客户结构失衡
- 区域结构失衡
- 渠道结构失衡
- 产品组合变化

### 4. 事件原因

- 某次活动
- 某个异常订单
- 某个短期业务事件

### 5. 系统原因

- 同步失败
- 字段约束缺失
- 数据映射错误

## 四、从问题走到动作

每个问题最终都应回答：

- 应该补什么数据？
- 应该找谁确认？
- 应该抽样检查什么？
- 后续应该持续关注哪个指标？

如果一个问题无法落到动作层，它通常还只是“有趣”，不是“有用”。

## 五、推荐输出句式

每个洞察块建议按下面顺序组织：

1. 现象
2. 为什么值得关注
3. 一个或多个原因假设
4. 这些假设分别缺什么证据
5. 建议下一步动作

## 六、推理边界

agent 不应：

- 把弱信号包装成强结论
- 把统计异常自动等同于经营异常
- 在没有业务上下文时过度解释
- 为了“显得深”而制造不可验证的判断
