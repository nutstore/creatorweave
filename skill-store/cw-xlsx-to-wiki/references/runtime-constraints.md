# Runtime Constraints

## Pyodide 运行约束

- 不使用 `subprocess`
- 不通过 CLI 包装器间接调用
- 直接导入 Python 模块并调用函数
- 每次新增 `import` 前，先评估会引入多少额外文件，避免因为依赖膨胀导致 Pyodide 内存溢出
- 转成 wiki 产物时，涉及写文件的逻辑应保持流式写入，避免一次性构造大内容后整体落盘

## 对 skill 的调用约束

- 优先通过 EO2Weave 的 `read_skill` / `read_skill_resource` 机制理解这个 skill，不要依赖一次性把全部资源塞进上下文
- 不要绕过 `scripts/run_workbook_tool.py` 和 `xlsx_skill_runtime.workbook_tools` 自行实现新的正式流程
- 不要自行写新的 OOXML 直改逻辑来替代当前 runtime
- 若需要扩展流程，优先在现有 runtime 导出函数之上增加薄适配层
- 如果运行时提供了 Python execution path，以该路径为准；不要根据项目目录结构手工猜测脚本绝对路径

## 数值精度约定

- 对金额、比率、份额、计数以外的可精确十进制业务值，默认使用 `decimal.Decimal` 理解、传递和比较
- 像 `1/3` 这类无法被二进制浮点精确表示的值，不能因为 Python `float` 的表示误差而改变业务含义
- 在引用 `data_bundle.txt`、旧版 `data.tsv`、`summary.yaml`、`workbook.yaml`、`regions.yaml` 等产物中的数字时，若没有额外声明，应按十进制文本值解释，再按需要转换为 `Decimal`
- 只有在字段天然是近似值时才使用 `float`
- 如果需要对外说明数值结果，优先保留原始十进制字符串，避免先转成 `float` 再序列化

## 数据溯源约束

- 对任意 `.xlsx` 文件进行读取、分析、汇总、比较或推导时，所有结果都必须明确标注数据来源位置
- 数据来源位置至少要精确到：工作表名、单元格坐标或单元格区间
- 如果一个结果由多个单元格或多个区间计算得到，必须列出所有参与计算的位置
- 如果一个结果经过了多步推导，必须说明每一步使用了哪些位置的数据以及采用了什么计算方法
- 不允许只写“来自某张表”或“来自某一列”这类无法精确定位的描述
- 任何中间结果都不能作为最终来源；最终说明必须追溯到原始单元格或原始区间
- 当输出文字结论时，结论后应同时给出来源说明和计算说明
- 如果无法确定某个结论对应的具体单元格或区间，则不得将该结论表述为确定事实

推荐输出格式：

```text
- 结论：总销量为 425
- 来源：Sheet1!D2:D18
- 计算：对 D2:D18 中的数值求和
```
